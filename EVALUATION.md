## 📏 Metrics

| Metric | Definition |
| --- | --- |
| ✅ **Planning success** | Planner returns a valid plan (`solved`) |
| 🤖 **Execution success** | Every plan action succeeds in MuJoCo (`success`) |
| ⏱️ **Planning time & plan length** | Wall-clock solve time (s) and number of grounded actions |
| 🔍 **Failure analysis** | Which tasks fail and what structures are hard |

ABD (Assembly-by-Disassembly) numbers from the WorkBenchMark paper are **not**
reproduced in this repo’s `results/` — we report our PDDL pipeline only.
Where the paper publishes ABD planning time / length, those can be compared
externally. This document focuses on the measured PDDL + MuJoCo run.

## 🔍 Failure analysis

**No planning or execution failures** on the 60 evaluated tasks.

## 🛠️ Improvements

What still could be improved:

1. **Tier-3 planning outliers** — especially `task_020` (~7 min). The model
   is complete enough to solve, but classical search cost is the gap to close
   (maybe by a stronger planner or using more advanced heuristics).
2. **Plan order vs. robot motion** — raw PDDL order can finish a column before
   other bases (valid symbolically, awkward for the arm). Playback uses
   `reorder_plan_bottom_up` so MuJoCo prefers layer order while keeping
   support-before-stack. That is an **execution** preference, not a planning
   failure. Also here a better solution could be to use a more advanced planner that can handle this, instead of implentig a custom solution.
3. **Box proxies / no studs** — stacked bricks stay put via kinematic pins
   (`duplo_hold`). Failures could show up as rigid body physics might behave differentl.
   With the pins, the measured metric is motion and grasp success against the symbolic plan.
4. **Out of scope** — Tier 4 interlocking, perception noise, and real-robot
   runs are not evaluated here (see README). This could be implemented as well, but would require a lot of work.
